Implementation roadmap

Build order for primeradiant

A staged plan for turning the Elixir architecture into a working product without losing the core invariant: live story state, not summaries.

0. Roadmap rule

Every phase must preserve the same product proof: input fragments become story state; story state produces user-relative deltas; agents propose with evidence; authored output is grounded and updates seen-state.

The first implementation target is not “an app.” It is a story-semantics proof harness whose only job is to prove or disprove the core model on a tiny fixed corpus.

Phase 1 — Story-semantics proof harness

Build

Tiny proof loop

  • Phoenix app + Repo + core Ecto schemas
  • Golden corpus loader
  • Canonical input normalization
  • Soup decision classifier
  • Proposal-backed graph writes
  • One “what changed for Flynn” output
Gate

Story decisions are real

  • New story / attach / update / no-op tests pass
  • Color, stale, and conflict cases are labeled with evidence
  • No committed graph truth is preseeded
  • Output is grounded in soup state, not broad summarization

Phase 2 — Contracts and soup API

Build

Formalize the harness

  • Context API tests exist
  • MCP tool contracts are stubbed
  • Basic full-text/vector indexing path
  • soup.search / expand / state / delta / provenance / propose
Gate

Evidence is immutable

  • Fixture inputs survive round-trip
  • Duplicate input detected without story rewrite
  • Private/public ACL tags preserved
  • Every Input has provenance

Phase 3 — First swarm loop

Build

Proposal-producing agents

  • Claim & Entity Extractor
  • Story Seeker
  • Connection Weaver
  • Development Detector
  • Staleness Keeper
Gate

Agents propose, not commit

  • JSON Schema validation
  • Ecto changeset validation
  • Evidence refs required
  • Generic related edges rejected

Phase 4 — Arbitration and projections

Build

Trusted graph state

  • Arbiter accepts/rejects/weak-commits proposals
  • GraphCommit audit trail
  • StoryStateSnapshot projection
  • Freshness, activity, gravity, unresolved count
Gate

Story state is rebuildable

  • Projection can be rebuilt from committed graph
  • Contradiction/supersession does not erase history
  • Stale state changes without deletion
  • User watch can raise personal relevance

Phase 5 — Authoring and seen-state

Build

What’s new to you

  • Author Planner
  • Soup Retriever evidence packets
  • Narrator + Verifier
  • AuthoredOutput records
  • Seen-State Recorder
Gate

No ungrounded output

  • Every material sentence has evidence refs
  • Second briefing excludes already-seen facts
  • Duplicate/no-op does not trigger fake update
  • User-specific privacy is preserved

Phase 6 — LiveView operator/product UI

Build

Visible story state

  • Story dashboard
  • Story detail with evidence/provenance
  • Proposal review queue
  • Watch creation for /preferences/priorities and /stories/concepts
  • Authored preview pane
Gate

Flynn can verify the product

  • Hybrid MVP demo runs end-to-end
  • Live updates appear via PubSub/LiveView
  • Proposal decisions are inspectable
  • Briefings show “new to you” correctly

Phase 7 — Real connectors after proof

Only after the golden corpus passes should real source adapters be added. Start with the smallest safe connectors:

  1. RSS/news article adapter for public inputs.
  2. Local/imported email-thread adapter for private thread inputs.
  3. Manual user watch/story seed entry.

Do not start here. Real connectors create noise before the story-state loop is proven.

Stop/go criteria

  • Go: proof harness produces correct new/attach/update/no-op/color/stale/conflict decisions, story nodes, named edges, and user-relative deltas.
  • Go: all graph mutations are proposals with evidence and arbitration trail.
  • Stop: the system can only prove itself through demo shortcuts or preseeded trusted state.
  • Stop: output quality depends on broad summarization rather than soup state and evidence packets.
