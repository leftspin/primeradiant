Product slice

MVP slice: prove story state

The first primeradiant build should prove the magic in one narrow loop: messy inputs become a living story, the system knows what changed, what went stale, and what is new to the user.

1. Recommendation

Build a hybrid slice: one public story, one private email/message thread, one user watch, and one stale/no-op case. Do not start with a generic news feed or a generic personal-memory product.

This slice forces the architecture to prove the things that make primeradiant different: cross-source story identity, private context, user-relative novelty, evidence-backed narration, and staleness.

2. Why hybrid, not “news first” or “email first”

News-only risk

Looks like aggregation

If v1 is only public articles, the product can accidentally become a smarter feed reader. That undersells the soup/API/user-state thesis.

Email-only risk

Looks like memory

If v1 is only private threads, the product can accidentally become thread summarization. That hides story gravity, public evidence, and cross-source relationships.

Hybrid value

Forces the real abstraction

The same story machinery must handle public evidence, private context, personal priority, repetition, and stale/no-change updates.

3. Golden corpus

Public story

Multi-source event

3–5 public inputs about one evolving event: initial report, follow-up, repeated report, contradiction or correction, and a framing/spin difference.

Private thread

Personal story

4–6 messages/emails around one ongoing personal task or decision: request, reply, unresolved question, later update, and duplicate/no-op reply.

User watch

Priority override

A watch created from /preferences/priorities or /stories/concepts that should matter even if global graph rank is low.

Stale/no-op case

Negative proof

An input that is related but not materially new, plus a story with no updates long enough to become dormant/stale without disappearing.

4. End-to-end demo path

  1. User creates a watch: “track this story/concept for me.”
  2. Public and private inputs arrive through source adapters.
  3. Canonicalization creates immutable Input nodes.
  4. Extractor proposes Claims and Entities.
  5. Story Seeker proposes a Story node when inputs become an evolving situation.
  6. Connection Weaver proposes named edges: supports, updates, duplicates, contradicts, adds_color, part_of, watch_applies_to.
  7. Arbiter commits or weak-commits validated proposals.
  8. Projection updates story state, gravity, freshness, unresolved questions, and user relevance.
  9. Author Planner decides whether to produce output.
  10. Narrator writes “what changed / what’s new to you” from evidence packet only.
  11. Seen-State Recorder marks exactly what the user was shown.

5. Acceptance criteria

  • Story identity: related public/private inputs attach to an evolving Story rather than sitting as separate summaries.
  • Named relationships: no committed edge is merely “related.”
  • Novelty: duplicate/reinforcing inputs do not create fake material updates.
  • Staleness: dormant stories change state without deletion or destructive rewrite.
  • User priority: a low-global-rank watch can still trigger personal relevance.
  • Seen-state: the second briefing says only what is new since the first briefing.
  • Grounding: every material authored sentence traces to evidence refs.
  • Agent safety: all graph-changing agents write proposals, not direct commits.

6. Out of scope for this slice

  • Full social/news ingestion at scale.
  • Multi-tenant enterprise administration.
  • Autonomous web crawling loops.
  • Graph explorer as primary UX.
  • Neo4j/Memgraph as source of truth.
  • Perfect ranking; only simple story gravity and user relevance are needed.
  • First-class Perspective/Facet/Question nodes unless the corpus proves they are necessary.

7. Next implementation move

Before building the product app, create a story-semantics proof harness. The harness should be small enough to inspect manually and rich enough to catch fake summarization.

Proof gate: the harness must decide, with evidence, which inputs create new stories, attach to existing stories, update story state, add color/spin, conflict, or do nothing. If it cannot produce those decisions and one grounded “what changed for Flynn” output without demo shortcuts or preseeded trusted state, stop before broader implementation.
