Use binary_id primary keys for production tables. Keep fixture IDs as explicit columns for import idempotency and test traceability, not as production identity.

6. Proposal Versus Committed State

  1. Proposals.submit/3 inserts a proposals row, one or more proposal_ops, and evidence refs. It does not write soup_nodes, stories, edges, conflicts, story_fact_versions, story_events, or seen_states.
  2. Arbitration.decide/3 writes proposal_decisions with evidence/confidence and changes proposal/op status. It still does not mutate graph truth.
  3. Arbitration.commit/2 is the only production context allowed to create graph_commits and apply accepted ops to committed state. It must reject unevidenced, already-decided, unsupported-edge, and ACL-inaccessible proposals before commit.
  4. soup_nodes, edges, conflicts, story_fact_versions, story_events, and story state updates must reference proposal_id, proposal_op_id, and graph_commit_id.
  5. Authoring.record_output/5 records authored output and evidence refs only after verification succeeds, creates the graph-visible authored output node, then calls UserContext.mark_seen_from_output/2. No other path may advance seen-state.
Raw input -> Input
Input + current story state -> Proposal + ProposalOps(per-op evidence/confidence)
ACL-aware proposal decision -> accepted/rejected/needs_more_evidence
Accepted ProposalOps -> GraphCommit -> SoupNodes / Stories / Edges / Conflicts / FactVersions / StoryEvents
Verified evidence packet -> AuthoredOutput + AuthoredOutputUnits + EvidenceRefs -> SeenState(input/claim/output refs)

7. Migration Sequence

  1. Create Postgres enums or text check helpers for node types, proposal status, op types, edge types, story state, conflict status, seen ref kinds, and authored output status. Text plus check constraints is acceptable for this slice.
  2. Create base typed tables: inputs, stories, watches, agent_runs, authored_outputs, and authored_output_units.
  3. Create proposal tables: proposals, proposal_ops, and proposal_decisions, including actor, per-op evidence refs, and per-op confidence.
  4. Create graph_commits.
  5. Create committed graph tables: soup_nodes, edges, story_fact_versions, story_events, and conflicts. Add required foreign keys to proposal/op/commit.
  6. Create user state tables: seen_states and seen_state_refs, including input/claim/output ref tracking.
  7. Create evidence_refs after all subject tables exist. Add foreign keys where direct references are known and keep subject_type/subject_id for polymorphic tests.
  8. Add indexes and unique constraints. Use concurrent indexes only if there is existing production data; for first schema creation, ordinary indexes are fine.
  9. Add fixture import task and seed only the synthetic tenant/user required by tests. Import expected artifacts as assertions only, never as preseeded trusted graph state.
  10. Add acceptance tests before any real connector, ranking, or UI work.

9. Fixture Import Path

The current proof harness remains the source of semantic fixtures. Production storage imports the fixture corpus through the same boundaries real data will use, while allowing a deterministic synthetic agent run for test repeatability.

  1. Read priv/fixtures/primeradiant_golden/manifest.json and fixtures from /Users/mike/shared-workspace/primeradiant/proof-harness.
  2. Create one synthetic tenant and user flynn for acceptance tests.
  3. Upsert fixture watches into watches by (tenant_id, user_id, watch_key).
  4. Upsert fixture inputs into inputs by (tenant_id, source_type, external_id) and content_sha256.
  5. Verify fixture input bodies are normalized prose, not trusted labels such as FACT, COLOR, BACKGROUND, or QUESTION directive lines.
  6. Run the production normalizer or import the harness-normalized facts into the same inputs columns. Do not import pre-trusted committed story state, classifier labels, graph nodes, graph edges, conflicts, or seen-state.
  7. Create a fixture agent_runs row with agent_type = fixture_story_seeker.
  8. For each normalized input, call Proposals.submit/... with the same op classes the harness emits, including create_input and per-op evidence refs/confidence.
  9. Call Arbitration.decide/... and Arbitration.commit/... for accepted fixture proposals. The test path must also exercise rejection for missing evidence, already-decided proposals, unsupported related edges, and private evidence hidden from the actor.
  10. Record the first Flynn briefing through Authoring.record_output/... only after verification and verify seen_states updates input refs, claim refs, and output refs from that output.
  11. Render the second Flynn delta from persisted state and verify no fake material update appears after seen-state.

Import rule: fixture import may accept fixture file order as an input stream, but it may not import expected story nodes, expected edges, expected proposals, expected story state, or expected briefings as trusted behavior. Expected artifacts remain inspectable assertions only.

11. Explicit Non-Goals

  • No real connectors. RSS, email, messages, web search, source adapters, and object storage ingestion are outside this slice.
  • No ranking/headliners. Watch priority may influence fixture authoring, but no global gravity/PageRank implementation is required.
  • No swarm scaling. One synthetic fixture agent run and context-level proposal submission are enough.
  • No broad UI. Proposal review, story dashboards, graph visualization, and LiveView screens wait for later slices.
  • No broad Claim/Entity extraction product. This slice persists the minimal claim/entity graph nodes required by the reconciled proof, but does not implement a general extraction system.
  • No destructive story merge, delete, or rewrite seen-state operation.

12. Risks and Open Questions

Residual risk

Story-key generation

The reconciled proof establishes the storage semantics for a supplied story_key. Production still needs a non-fixture story identity algorithm before real ingestion, but that is outside this storage/schema slice.

Residual risk

Narrow conflict detection

The current proof detects conflicts through narrow structural fact keys. Persisting story_fact_versions and conflicts preserves provenance, but broader contradiction discovery remains a later agent/projection problem.

Residual risk

Polymorphic evidence refs

evidence_refs.subject_type/subject_id keeps the slice small, but Postgres cannot enforce all polymorphic foreign keys. Direct nullable FKs cover known v1 subjects; changesets must enforce the subject contract.

Residual risk

JSONB versus normalized facts

Current facts/background/questions are simple maps. story_fact_versions normalizes structural facts for provenance, while stories.structural_facts remains a read projection. Keep this split explicit in tests.
