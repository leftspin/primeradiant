Production semantics slice after T312 validation

Real ingestion and story identity semantics

Defines the next narrow Primeradiant slice: accept real source items through a manual admission seam, normalize them with provenance, decide story identity without trusted fixture labels, and submit proposal-backed story changes through the validated storage schema.

2. Goal and Cut Line

Goal

Replace fixture-shaped identity

Define production story identity behavior for real admitted source items where fixture_id, file order, expected artifacts, and title-derived labels cannot drive decisions.

Smallest slice

Manual real ingestion

Accept real items through an explicit ingestion API or batch file, normalize them, retrieve candidate stories, classify identity decisions, and persist proposal-backed changes.

Boundary

Semantics only

No connectors, ranking/headliners, autonomous acquisition, broad UI, swarm scaling, deployment, or production daemon in this slice.

3. Input Admission Contract

Before connectors exist, real source items enter through a controlled admission seam. The caller can be a Mix task, test helper, admin-only context call, or local batch import. It is not a connector and must not contain story labels.

3.1 Accepted Item Shape

{
  tenant_id: uuid,
  ingestion_run_key: string,
  source_type: "news_article" | "opinion_column" | "email" | "message" | "document" | "user_note" | "web_page",
  source_mode: "manual_real_ingest_v1",
  external_id: string,
  observed_at: utc_datetime_usec,
  retrieved_at: utc_datetime_usec,
  occurred_at: utc_datetime_usec | null,
  canonical_uri: string | null,
  raw_object_uri: string | null,
  source_name: string | null,
  source_actor: {kind: string, name: string | null, stable_id: string | null},
  title: string | null,
  body_text: string | null,
  extracted_text: string | null,
  metadata: map,
  acl: {privacy: "public" | "private", participants?: [string]},
  content_sha256: string | null
}

3.2 Admission Rules

  • tenant_id, source_type, external_id, observed_at, retrieved_at, acl, and at least one readable text body or raw object reference are required.
  • external_id must be stable within (tenant_id, source_type). For manually captured public URLs, use canonical URL plus retrieval timestamp or source-provided ID. For private items, use source account/thread/message ID if available; otherwise use an importer-provided stable ID.
  • content_sha256 is computed from canonicalized text and raw object metadata when omitted. It remains the exact duplicate fingerprint, not story identity.
  • fixture_id is forbidden for real admission. Test imports may keep fixture_id only inside fixture-specific code paths.
  • Admission rejects metadata fields named expected_role, story_hint, expected_story, expected_classification, edge_hints, or equivalent labels. Those names may appear only in fixture expected artifacts used as assertions.
  • Admission writes an immutable inputs row or returns the existing row for (tenant_id, source_type, external_id) or exact content_sha256. It does not create stories, edges, facts, conflicts, seen-state, or authored outputs.
  • Private inputs require acl.privacy = "private" and a non-empty participant list before the item can become evidence for proposals or authoring.

4. Normalized Input Envelope

The normalizer converts admitted items into a deterministic envelope for candidate retrieval and proposal building. It may use rules, local extractors, or model-assisted structured extraction, but the stored result must be schema-validated and evidence-span backed.

{
  input_id: uuid,
  tenant_id: uuid,
  source_type: string,
  external_id: string,
  observed_at: utc_datetime_usec,
  retrieved_at: utc_datetime_usec,
  occurred_at: utc_datetime_usec | null,
  title: string | null,
  body_text: string,
  acl: map,
  provenance: {
    ingestion_run_key: string,
    source_mode: "manual_real_ingest_v1",
    source_name: string | null,
    source_actor: map,
    canonical_uri: string | null,
    raw_object_uri: string | null,
    content_sha256: string,
    normalizer_version: string,
    extractor_version: string | null,
    trace_id: string | null
  },
  extracted: {
    claims: [{claim_key, text, fact_key?, fact_value?, polarity, modality, time_scope, span}],
    entities: [{entity_key, kind, name, aliases, span}],
    events: [{event_key, text, time_scope, span}],
    questions: [{question_key, text, status, span}],
    colors: [{color_key, text, framing_kind, span}],
    topic_tokens: [string],
    source_posture: {kind, certainty, attribution}
  }
}

4.1 Required Provenance Fields

  • Every claim, entity, event, question, and color item carries a text span or evidence label that can become an evidence_refs row.
  • The envelope records normalizer_version. Changes to extraction behavior must be visible in tests and should not silently rewrite prior input rows.
  • source_posture distinguishes reporting, opinion, correction, firsthand message, user note, and unknown source posture. It is evidence context, not a shortcut to a story decision.
  • Time fields are preserved separately: observed_at is when Primeradiant saw it, retrieved_at is when the item was fetched/imported, and occurred_at is only set when the text supports an event time.

5. Candidate Story Retrieval

Candidate retrieval is recall-oriented. It gathers plausible existing stories and neighboring evidence for the identity decision. It does not rank stories for users, pick headliners, or decide user-facing importance.

5.1 Inputs to Retrieval

  • Normalized topic tokens, entity keys, claim fact keys, claim values, event time windows, source type, observed time, and ACL scope.
  • Exact duplicate keys: (tenant_id, source_type, external_id) and content_sha256.
  • Candidate story fields: story_key, title, state, version, structural facts, background facts, questions, colors, topic tokens, first/last observed time, last material time.
  • Graph evidence: supports, updates, duplicates, contradicts, adds_color, part_of, and watch_applies_to edges visible to the actor.
  • Visible fact versions, conflicts, story events, and evidence refs for each candidate story.

5.2 Allowed Retrieval Methods

  • Exact source/content dedupe lookup.
  • Token/entity/fact-key overlap against stored inputs and stories.
  • Postgres full-text search over title/body/topic tokens.
  • Optional embedding similarity if already available in the implementation, scoped to candidate retrieval only.
  • Time-window filters that favor recent active stories but still include stale/background stories when entity/fact overlap is strong.

5.3 Forbidden Retrieval Shortcuts

  • No fixture IDs, file order, expected artifact IDs, or fixture story labels.
  • No global ranking, headliner scoring, popularity scoring, or feed placement.
  • No broad summarization prompt that receives all stories and returns an unstructured answer.
  • No use of private candidate evidence unless the actor can access it.

6. Story Identity Decision Model

The decision model returns one primary decision per admitted input plus zero or more proposed edges/fact/conflict/state ops. Decisions are evidence-backed proposals, not committed truth.

DecisionWhen to useRequired proposal behavior
attach The input belongs to an existing story and adds either new evidence, first structured facts, background, questions, or source weight without requiring a new story identity. attach_input, record_event, and at least one named edge such as supports, updates, duplicates, or adds_color.
split The input shares topic/entity vocabulary with a candidate story but describes a distinct evolving situation with different structural facts, actor/action, venue, scope, or time boundary. create_story, attach_input, fact/event ops, and no destructive merge. A parent relation may be proposed separately as part_of.
part_of The input or newly split story is best understood as a substory/facet of a larger existing story, while keeping its own identity. attach_story_part_of using story-node endpoints. Must not collapse story keys or move inputs from one story to another destructively.
conflict Incoming supported claims disagree with current story facts or claim nodes on the same fact key and compatible scope. record_conflicts, contradicts edge, story_fact_versions with replacement only when arbitration accepts correction semantics.
no_op The input is an exact duplicate or repeats already-current facts without new material facts, questions, conflict, or useful color. attach_input and duplicates or support/source-weight event. It must not advance last_material_at or emit a user-facing material delta.
color The input adds framing, source posture, attribution, human context, or interpretation without changing structural facts. append_colors, adds_color, and record_event. It does not update structural facts or material delta unless separately justified.
stale The input is a check-in/background note indicating no new activity, or a maintenance pass finds a story dormant long enough to change activity state. merge_background or mark_state plus record_event. Story remains present; no delete or destructive rewrite.

6.1 Decision Output Contract

{
  input_id: uuid,
  decision_type: "attach" | "split" | "part_of" | "conflict" | "no_op" | "color" | "stale",
  candidate_story_id: uuid | null,
  proposed_story_key: string | null,
  parent_story_id: uuid | null,
  changed_facts: map,
  conflicting_facts: [{fact_key, prior_fact_version_id, prior_value, incoming_value, scope, evidence_refs}],
  rationale: string,
  confidence: decimal_0_to_1,
  evidence_refs: [evidence_ref_input],
  abstained_candidates: [{story_id, reason}]
}

6.2 Identity Evidence Rules

  • Topic overlap alone is never enough for attach. At least one structural compatibility signal must exist: shared entity plus same event/action, shared fact key with compatible value, same source thread, exact duplicate content, or explicit textual continuity.
  • Shared venue or actor with a different action can justify split plus optional part_of, not attach.
  • Private thread continuity can support attach when message IDs, participants, subject, and text support the same task or decision.
  • Opinion/framing items attach as color only when they discuss an existing story and do not assert incompatible structural facts.
  • When evidence is below threshold, return needs_more_evidence proposal status or abstain; do not create generic relation edges.

7. Story Key Generation and Collision Handling

story_key remains stable production identity, but the generation algorithm must stop relying on fixture names or the first three title tokens.

7.1 Key Generation

  • For split or new-story creation, generate a canonical key from normalized identity anchors: primary entity or venue, action/situation, and disambiguating scope or time when needed.
  • Keys are lowercase ASCII slugs. Strip punctuation, normalize whitespace, remove stopwords, and cap length. Store a richer title separately.
  • The key input set must be recorded in the proposal payload as identity_anchors so reviewers can inspect why that key was proposed.
  • Do not include fixture_id, importer filename, external ID, source hostname alone, or source title alone as the key basis.

7.2 Collision Handling

  • Before proposing create_story, lookup (tenant_id, story_key). If an existing story has the same key and compatible identity, propose attach instead.
  • If an existing story has the same key but incompatible identity, append a deterministic disambiguator derived from identity anchors, such as venue, actor, or first observed date. Record the collision in proposal rationale.
  • If two candidate keys differ but identity evidence strongly indicates one story, attach to the existing story and preserve the original key.
  • Never rename an existing story key in this slice. Key correction requires a future explicit migration/proposal type.

8. Conflict and Contradiction Detection

The current proof detects conflicts mainly through correction wording and simple fact deltas. Real ingestion needs a bounded contradiction model that still fits the storage schema.

8.1 First Implementation Bounds

  • Only compare normalized claims that have a fact_key, fact_value, polarity, and scope. Free-form semantic contradiction without fact keys is out of scope.
  • Support these fact kinds first: status/state, numeric amount/count, schedule/time, availability/service state, ownership/responsibility, location/venue, and deadline.
  • Scope must be compatible before conflict: same story candidate, same fact key, overlapping time scope, and no clear change-over-time relation.
  • Correction wording is a signal, not a requirement. A conflict can be detected when values are incompatible even if the source does not say "corrected" or "contradiction."
  • Change over time is not automatically conflict. If a later input says the service moved from halted to normal after a resolution event, propose updates and fact replacement with provenance; if it disputes the prior report's truth for the same time scope, propose conflict.

8.2 Conflict Output

{
  fact_key: string,
  prior_fact_version_id: uuid,
  prior_value: string,
  incoming_value: string,
  comparison_type: "mutually_exclusive_value" | "numeric_delta" | "time_scope_overlap" | "negated_claim",
  scope: {story_id, time_scope, entity_keys},
  proposed_status: "open" | "accepted_correction",
  evidence_refs: [evidence_ref_input],
  confidence: decimal_0_to_1
}

A proposed correction may update current story facts only through accepted record_conflicts and merge_facts ops. The conflict record remains durable even after resolution.

9. Proposal and Arbitration Requirements

This slice uses the validated storage schema without expanding it unless implementation discovers a blocker. New behavior is expressed as stricter proposal payloads, tests, and context rules.

9.1 Required Proposal Ops by Decision

DecisionMinimum opsAllowed edge types
attachcreate_input if not admitted, attach_input, record_event, optional fact/background/question opssupports, updates
splitcreate_story, attach_input, merge_facts, record_eventsupports, updates
part_ofattach_story_part_of, record_eventpart_of
conflictrecord_conflicts, record_event, optional merge_facts after accepted correctioncontradicts
no_opattach_input, record_eventduplicates or supports
colorappend_colors, record_eventadds_color
stalemerge_background or mark_state, record_eventsupports when input-backed; none required for maintenance-only state mark

9.2 Arbitration Gates

  • Reject any proposal or op without per-op evidence refs and confidence.
  • Reject any proposal whose actor cannot read the admitted input or candidate story evidence.
  • Reject attach when identity evidence is only topic overlap.
  • Reject split when it creates a story key collision without a collision rationale.
  • Reject conflict when fact scope is missing or incompatible.
  • Reject any attempt to mutate committed graph rows outside Arbitration.commit/2 and graph_commits.
  • Reject related, adjacent_to, reframes, or mentions edge commits in this slice because the validated storage schema does not allow them yet.

11. Tests and Evals

The acceptance suite must prove the new path is not fixture-shaped demo code.

11.1 Required Test Packs

  • Real-style public pack: 8 to 12 admitted public items with source URLs or raw object refs, no fixture IDs, no story hints, mixed source posture, and at least one attach, split, part_of, conflict, no_op, color, and stale/background case.
  • Real-style private pack: 5 to 8 private messages/emails/user notes with participants, thread continuity, an unresolved question, a later material update, and one ACL rejection case.
  • Collision pack: two stories that produce the same initial slug but are structurally distinct, plus a later item that correctly attaches to one of them.
  • Conflict scope pack: one true contradiction, one update-over-time that is not conflict, one opinion/framing item that is not fact conflict, and one low-confidence abstention.

11.2 Acceptance Checks

  1. Real admission rejects fixture_id, story_hint, expected_role, and equivalent trusted labels.
  2. All admitted inputs persist with required provenance and ACL.
  3. Candidate retrieval returns visible candidate stories and evidence without ranking/headliner fields.
  4. Each required decision type appears at least once: attach, split, part_of, conflict, no_op, color, stale.
  5. No decision is based solely on title overlap or source filename.
  6. Story key collisions are deterministic and non-destructive.
  7. Conflict detection catches incompatible fact values without correction wording.
  8. Change-over-time is not misclassified as conflict when time scope differs.
  9. Every graph mutation passes through proposals, proposal ops, accepted decisions, graph commits, evidence refs, and confidence.
  10. No committed edge has type related.
  11. Private evidence is unavailable to unauthorized actors in retrieval, proposals, arbitration, authoring, and seen-state.
  12. Golden fixture tests still pass with fixture-only assumptions isolated.
  13. Storage harness and live Postgres schema validation still pass.

11.3 Forbidden Pass Conditions

  • A test can pass by matching a fixture ID, filename, manifest order, expected artifact, or hard-coded title phrase.
  • A conflict test passes only because the title contains "correct" or "contradiction."
  • A near-collision test creates a destructive merge or rewrites an existing story key.
  • A no-op duplicate advances last_material_at or appears as a material user delta.
  • Proposal payloads contain evidence-free rationales that arbitration accepts.

12. Exact Next Implementation Slice

  1. Add a real-admission module in the storage harness or next Phoenix context boundary: Primeradiant.Ingestion.Admission.admit_source_item/2. It validates the real item shape, rejects fixture labels, computes hashes, and persists/returns an inputs row.
  2. Add Primeradiant.Ingestion.RealNormalizer.normalize/1 with generic claim/entity/event/color/question output and span-backed provenance. Initial extraction can be deterministic/rule-based, but it must not contain corpus-specific ferry/roof/sensor shortcuts.
  3. Add Primeradiant.StoryIdentity.Candidates.retrieve/2 using exact dedupe, visible token/entity/fact overlap, and time windows. It must return candidate evidence packets, not rankings.
  4. Add Primeradiant.StoryIdentity.Decider.decide/3 implementing the seven decision types and bounded conflict checks.
  5. Map decisions to existing proposal ops and storage commit paths. Do not add tables unless a failing test proves the current schema cannot represent the behavior.
  6. Add the four real-style test packs and keep the existing proof/storage harness tests green.
  7. Run proof harness tests, storage harness tests, and live Postgres schema validation before reporting readiness.

13. Explicit Non-Goals

  • No RSS, email, message, web-search, or social connector implementation.
  • No broad UI, story dashboard, proposal review UI, or authored briefing UI.
  • No ranking, headliner selection, popularity scoring, feed placement, or alert threshold system.
  • No swarm scaling, Oban production lanes, autonomous acquisition loop, or production daemon.
  • No deployment, Docker release, persistent service operation, or production secrets/configuration.
  • No new first-class graph source of truth outside Postgres.
  • No broad semantic contradiction engine beyond bounded fact-key/value/scope checks.
  • No story-key rename or destructive story merge flow.

15. Blockers and Residual Risks

Extraction quality risk: Real source items require generic claim/entity/fact extraction. A deterministic first pass can prove the boundary, but it may under-detect conflicts until model-assisted structured extraction is added and evaluated.

Schema fit risk: The validated schema can represent this slice, but it does not have first-class raw source rows or source artifacts. This spec uses the existing inputs.object_uri, normalized, and provenance payloads until a future raw-source schema is explicitly specified.

Edge vocabulary risk: Architecture docs mention mentions, reframes, and adjacent_to, but storage validation currently allows only supports, updates, duplicates, contradicts, adds_color, part_of, and watch_applies_to. This slice follows storage until a separate edge expansion spec exists.

Implementation blocker if encountered: If the storage harness cannot persist real admitted inputs without fixture IDs, implementation must stop and patch the admission/storage path first. Do not compensate by filling fake fixture IDs.
