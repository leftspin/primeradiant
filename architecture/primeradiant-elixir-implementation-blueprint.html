Implementation blueprint

primeradiant in Elixir

A senior-engineer-ready shape for turning the architecture into a Phoenix system without writing application code yet.

1. Build stance

Decision: primeradiant should be an Elixir/Phoenix system because the product is a living supervised swarm, not a request/response CRUD app with some agents bolted on.

Runtime truth

OTP boundaries first

Ingestion, model calls, proposal generation, arbitration, projections, and authoring should fail small and restart cleanly.

Data truth

Postgres remains the soup

Ecto schemas and changesets are the gate before any agent proposal becomes durable graph state.

UX truth

LiveView is native

Story state is alive. Dashboards, proposal review, watches, and “what changed” should update without frontend sprawl.

2. Phoenix contexts and umbrella shape

Use a single Phoenix app until the seams prove they need physical separation. Keep domains separated as contexts and supervised workers, not premature services.

Primeradiant
├── Primeradiant.Repo
├── Primeradiant.Soup              # nodes, edges, story state, provenance
├── Primeradiant.Ingestion         # source adapters, canonical input creation

├── Primeradiant.Authoring         # evidence packets, planner, narrator outputs
├── PrimeradiantWeb                # LiveView + JSON API
└── PrimeradiantMCP                # MCP tools backed by contexts

7. First proof cut

The first code should be a story-semantics proof harness, not a product app. Its job is to answer whether the soup model can make and defend story-state decisions on a tiny corpus.

  1. Create Phoenix app, Repo, Oban, pgvector migration, and base supervision tree.
  2. Define Ecto schemas and changesets for RawSource, Input, SoupNode, SoupEdge, Proposal, AgentRun, UserWatch, UserSeenState, AuthoredOutput.
  3. Implement contexts as empty/contract-tested shells before agent work.
  4. Create one fixture corpus: public news story, private email thread, user watch, stale/no-op case.
  5. Normalize each fixture into canonical input records with source, timestamp, actors/entities, claims, links, raw text, ACL, and provenance.
  6. Classify each input as new story, attach to story, substantive update, repeated/no-op, color/spin, stale, or conflict.
  7. Write proposal-backed graph changes with evidence and confidence; no committed graph truth may be preseeded to make the proof pass.
  8. Build soup.search, soup.expand, story.state, story.delta, soup.provenance, soup.propose as JSON endpoints and MCP tools backed by fixtures.
  9. Implement first Oban pipeline: raw input → canonical input → extractor proposal → arbiter commit → projection update.
  10. Produce one authored output: what changed for Flynn since last seen, and why, with evidence references.

8. Non-negotiable gates

  • Gate: no agent can write committed soup state directly; proposals only.
  • Gate: every graph-changing output validates through JSON Schema and Ecto changesets.
  • Gate: every authored sentence can trace back to inputs/claims/proposals.
  • Gate: seen-state is updated from authored outputs, not inferred from story existence.
  • Gate: staleness is story/claim/input/user-relative state, not just a timestamp.
  • Gate: graph analytics and optional external workers are projections, never source of truth.
  • Gate: the proof harness must pass explicit attach/new/update/no-op/color/stale/conflict expectations without demo shortcuts, preseeded trusted state, or broad summarization.

This stops one step before code: the next owner can create the Phoenix project and start by turning these contexts, schemas, queues, and gates into tests.
