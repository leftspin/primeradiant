primeradiant architecture

A technical design for building the agentic storytelling system: selected technology, named seams, data model, agent catalog, prompt kernels, workflows, and MVP cut line.

System: primeradiant Category: agentic storytelling Audience: senior engineer / architect Status: implementation-ready design, not code Last updated: 2026-05-13

0. Executive architecture

primeradiant is not a memory store. It is a live story-state system. Its job is to ingest fragmented inputs, maintain a semantically rich story graph, let agents spelunk that graph, and author user-relative updates: what matters now, what changed, what is stale, and what is new to this user.

Source adapters
News, RSS, web pages, email, messages, social posts, documents, user story seeds.
↓
Canonical input pipeline
Normalize, classify, extract text, embed, dedupe, store immutable source record.
↓
Soup core
Typed graph of Inputs, Stories, Claims, Entities, User Watches, and named Edges with provenance.
↕
Agentic soup API
Search, traverse, inspect provenance, ask for deltas, follow unresolved questions, and propose graph changes.
↕
Swarm workflows
Specialized agents propose stories, connections, contradictions, developments, staleness changes, and larger-story structure.
↓
Projection layer
Story state, freshness, rank/gravity, user relevance, and “what changed” materialized for fast reads.
↓
Authoring system
Planner + retriever + narrator + verifier + seen-state writer produce grounded updates for each user.

Design stance: use a boring, auditable core store first. Let agents be creative at the proposal layer, not in the committed truth layer.

1. Architectural invariants

Story over item

Incoming inputs are evidence. The maintained object is the evolving story state.

State over memory

The system tracks freshness, staleness, deltas, unresolved questions, and per-user seen-state.

Proposals before commits

Swarm agents propose changes with evidence and confidence. A controlled seam commits durable graph state.

Named relationships

Edges are never just “related.” They say supports, contradicts, updates, duplicates, reframes, part-of, etc.

Web search is acquisition

External search gathers evidence. It does not bypass the soup as the situated reality layer.

User-relative output

The authoring system always asks: what has this user already seen, and what is new to them?

2. Selected technology

This selection optimizes for agent-written correctness, living-system concurrency, auditability, privacy control, and operational simplicity. Hiring-market breadth is intentionally not a selection criterion. The stack should fit primeradiant's shape, not the average web app.

Stack decision: use Elixir/Phoenix as the application substrate. OTP is not an implementation detail here; it is the natural runtime model for supervised swarm agents, evented ingestion, story-state maintenance, and live user-facing updates.

Backend/API

Elixir · Phoenix · Ecto

Elixir fits primeradiant's living-system shape: concurrent agents, supervised workers, evented story updates, subscriptions, and fault-tolerant ingestion. Phoenix gives HTTP, channels, and LiveView; Ecto keeps Postgres explicit and migration-friendly.

System of record

PostgreSQL 17 + pgvector

Postgres stores raw inputs, graph nodes/edges, proposals, story states, seen-state, audit logs, and embeddings. Graph is represented with typed node/edge tables first; no separate graph SoR.

Raw artifacts

S3-compatible object storage

Store source HTML, email MIME, attachments, screenshots, PDFs, and extracted text artifacts in object storage. Postgres stores metadata and content hashes.

Search

Postgres full-text + pgvector hybrid

Use BM25-ish full-text + vector similarity + reranking. Add OpenSearch/Qdrant only if scale proves Postgres insufficient.

Workflows/jobs

Oban · Oban Pro when justified

Oban runs ingestion, swarm passes, authoring, retries, scheduled staleness checks, and durable job observability inside the Phoenix/Postgres stack. Start there; do not add an external workflow engine until the product proves it needs one.

Agent API

MCP server + Phoenix JSON API

MCP exposes soup spelunking tools to agents. Phoenix JSON endpoints serve product UI and internal services. Both call the same domain/context layer.

Models

Model adapter + structured outputs

Use provider-agnostic LLM adapters. Require JSON Schema-validated outputs and Ecto changeset validation for all graph-changing agents. Keep prompt versions in the database.

Embeddings

Local-private default, cloud-optional

For private inputs, default to local embeddings such as BGE-M3 or nomic-embed-text. Public/news data may use cloud embeddings if policy allows.

Graph analytics

Materialized projections + optional analysis worker

Compute story gravity/PageRank-like scores from Postgres edge snapshots. Start with SQL/Ecto projection jobs. If heavier graph math is needed, put Python/NetworkX or graphblas behind the projection seam. Do not make it source of truth.

Frontend

Phoenix LiveView

Story dashboards, live updates, watches, proposal review, correction UI, and provenance views map naturally to LiveView. If graph visualization needs custom rendering, isolate it behind a small web component rather than changing the app shell.

Observability

OpenTelemetry + Langfuse + Prometheus

Trace every ingestion, agent run, prompt version, proposal, commit, author output, cost, and error. Agents without traces are bugs.

Deployment

Elixir release + Docker Compose first

Compose is enough for first production-ish deployment: Phoenix release, Postgres, object store, and worker nodes. Kubernetes can wait until load/ops needs justify it.

Explicit non-selection for v1: do not use Neo4j/Memgraph as the primary truth store yet. If needed, add a read-only graph projection later. The committed graph, proposals, audit, user state, and raw evidence should start in one transactional store.

Elixir runtime shape

Phoenix contexts

Domain boundaries

Use contexts such as Primeradiant.Soup, Primeradiant.Ingestion, Primeradiant.Proposals, Primeradiant.Authoring, and Primeradiant.UserContext. Contexts own rules; controllers, LiveViews, MCP tools, and workers call contexts.

OTP supervision

Failure containment

Run source adapters, model clients, MCP server, projection workers, and live subscription broadcasters under explicit supervisors. A bad connector or stuck agent pass must fail small, restart cleanly, and leave audit traces.

Oban queues

Agent execution lanes

Separate queues for ingestion, extraction, swarm proposals, arbitration, projections, authoring, and maintenance. Queue names become operational vocabulary and backpressure controls.

PubSub

Living story updates

Use Phoenix.PubSub to broadcast committed story-state changes, proposal review updates, watch matches, and authored-output readiness to LiveView dashboards and subscription workers.

3. Named seams

These seams are the boundaries a senior engineer should preserve. Each seam should have typed contracts, tests, audit, and ownership.

S1 · Source Adapter Seam

Outside world → RawInputEnvelope

Connectors normalize external sources into a minimal envelope without deciding story meaning.

{ sourceType, externalId, observedAt, actor, uri, rawObjectUri, extractedText?, metadata, acl }
S2 · Canonical Input Seam

RawInputEnvelope → Input node

Extract text, classify source, dedupe by content hash, embed, and create an immutable Input node.

S3 · Soup Core Write Seam

Committed graph mutation

The only seam allowed to commit durable nodes/edges/story state. It accepts validated operations, not free-form agent text.

S4 · Proposal Seam

Agent output → proposed operations

All swarm agents write proposals with evidence, confidence, and intended graph operations. Proposals are inspectable and reversible.

S5 · Agentic Soup API Seam

Agents → soup spelunking

Search, traverse, delta, provenance, unresolved questions, watches, and proposal submission. This is how agents reason from current situated truth.

S6 · Arbitration Seam

Proposal → commit / reject / weaken

Rules and arbiter agents decide whether proposed graph changes become committed state, remain weak, or are rejected.

S7 · Projection Seam

Graph/events → read models

Build story state, freshness, gravity rank, user relevance, and delta projections. Projections are derived and rebuildable.

S8 · User Context Seam

User state → watches/seen-state/preferences

Tracks subscriptions, priorities, corrections, authored outputs, and what each user has seen at story/input/claim/output granularity.

S9 · Authoring Seam

Evidence packet → user-facing output

The authoring system writes only from a bounded evidence packet and records what it showed the user.

S10 · External Acquisition Seam

Soup gap → source search/fetch

When the soup lacks evidence, acquisition can fetch web/news/public sources and re-ingest them as inputs. It does not directly author claims.

S11 · Audit/Trace Seam

Every action → durable trace

Agent runs, prompt versions, model calls, proposals, commits, and author outputs are logged with correlation IDs.

4. Core data model

Use Postgres as the system of record. Treat graph, proposals, story state, and user state as first-class relational structures with JSONB for flexible attributes.

Minimum viable node types

Input

An immutable incoming item: article, email, post, message, document, alert, user note.

Story

An evolving narrative object with state, freshness, developments, and relationships.

Claim

An atomic assertion extracted from inputs or story synthesis.

Entity

People, orgs, products, places, accounts, projects, agencies, etc.

UserWatch

A user-submitted priority/story seed/subscription target.

AuthoredOutput

A thing the system told a user, used for seen-state and accountability.

Later first-class nodes

Facet, Perspective/Spin, Question/Unknown, Development/Event, Source, Collection, and Correction can start as attributes/prompt concepts and become nodes when behavior proves they need durable relationships.

Core tables

raw_sources(id, tenant_id, source_type, external_id, observed_at, checksum, object_uri, acl, metadata)
inputs(id, raw_source_id, title, body_text, source_type, actor, occurred_at, observed_at, canonical_uri, embedding, attrs)
soup_nodes(id, tenant_id, node_type, title, summary, state, attrs, embedding, created_by, created_at, updated_at)
soup_edges(id, tenant_id, from_node_id, to_node_id, edge_type, confidence, status, evidence_refs, attrs, created_by, created_at)
proposals(id, tenant_id, agent_type, agent_run_id, proposed_ops, evidence_refs, confidence, status, rationale, created_at)
story_state_snapshots(id, story_id, version, freshness, activity_state, gravity_score, unresolved_count, state_json, created_at)
user_watches(id, user_id, node_id, intent, priority, filters, created_at, status)
user_seen_state(id, user_id, story_id, seen_story_version, seen_input_ids, seen_claim_ids, seen_output_ids, last_briefed_at)
authored_outputs(id, user_id, story_id, output_type, content, evidence_refs, story_version, created_at)
agent_runs(id, agent_type, prompt_version, model, scope, input_refs, output_json, cost, trace_id, status, started_at, ended_at)

Edge types for v1

  • mentions — Input/Claim mentions Entity.
  • supports — Input supports Claim or Story.
  • updates — Input adds a development to Story.
  • duplicates — Input repeats the substance of another Input/Claim.
  • contradicts — Claim/Input conflicts with Claim/Story state.
  • reframes — Input changes the interpretation or source framing.
  • adds_color — Input adds useful context but not a material development.
  • part_of — Story is substory/facet of larger Story.
  • adjacent_to — Stories are related but should not collapse.
  • watch_applies_to — UserWatch attaches to Story/Input/Entity/Claim.

5. Agentic Soup API

This is the core product API for agents. It should be available as MCP tools and backed by the internal domain service. Agents should use this before web search when the question concerns current story state, personal context, prior inputs, or user-specific novelty.

soup.search

Natural-language and filtered search across nodes, inputs, stories, claims, entities, and watches.

{ query, nodeTypes?, userId?, since?, limit? }

soup.expand

Traverse from seed nodes by edge type, direction, confidence, depth, and time window.

{ seedNodeIds, edgeTypes?, depth, strategy }

story.state

Return current story projection: freshness, activity, latest developments, unresolved questions, substories, and rank.

story.delta

Return what changed since a timestamp, story version, authored output, or user seen-state.

{ storyId, since: { userId } | { version } | { time } }

soup.provenance

Trace a node, edge, claim, or authored sentence back to inputs, agents, proposals, and commits.

soup.unresolved

Return open questions, low-confidence claims, contradictions, or missing evidence for a story.

watch.create / watch.update

Create user story seeds and priority anchors; connect them to graph nodes as evidence appears.

soup.propose

Submit graph operations as proposals, never raw commits, unless caller has committer authority.

{ agentRunId, ops[], evidenceRefs[], confidence, rationale }

author.evidencePacket

Build a bounded, citable packet for authoring: story state, deltas, inputs, claims, provenance, and seen-state.

6. Workflows

6.1 Ingestion workflow

  1. Source adapter receives/fetches external item and writes raw_sources.
  2. Canonicalizer extracts text, normalizes metadata, computes hashes, embeds content, creates Input node.
  3. Claim/Entity Extractor proposes Claim and Entity nodes and mentions/supports edges.
  4. Story Seeker and Connection Weaver inspect nearby soup and propose Story nodes/edges.
  5. Arbitration promotes valid proposals to committed soup nodes/edges.
  6. Projection jobs update story state, gravity, freshness, unresolved questions, and user-watch matches.
  7. Author Planner decides whether any user-facing update is warranted.

6.2 Maintenance workflow

  1. Scheduled Oban job selects active/stale/high-change story regions.
  2. Staleness Keeper updates freshness/activity proposals.
  3. Contradiction Scout and Perspective Scout scan for drift, conflict, and framing changes.
  4. Larger-Story Cartographer proposes new higher-level stories; it does not destructively merge old ones.
  5. Gravity jobs recompute rank and user relevance projections.

6.3 User briefing workflow

  1. Trigger: user asks, subscription fires, story delta crosses threshold, or scheduled digest runs.
  2. Author Planner chooses output type: breaking story, update, digest, explainer, thread catch-up, or no-op.
  3. Retriever builds evidence packet from soup API, including per-user seen-state.
  4. Narrator drafts concise user-facing text.
  5. Verifier checks every claim against evidence packet and marks uncertainty.
  6. Seen-State Writer records story version, inputs/claims shown, and authored output ID.

6.4 Agent spelunking workflow

  1. External agent starts with soup.search instead of web search.
  2. Agent expands graph around candidate stories/entities/inputs.
  3. Agent asks for story state, deltas, unresolved questions, and provenance.
  4. If soup lacks evidence, agent requests acquisition through the External Acquisition Seam.
  5. Agent answers from situated soup truth and may submit proposals for newly discovered structure.

7. Agent catalog and prompt kernels

These are prompt sketches, not final production prompts. Production prompts should include schema, examples, abstention rules, and version IDs. Every graph-changing agent must output structured JSON and cite node/input IDs.

Claim & Entity Extractor

Purpose: turn a new Input into candidate Claims and Entities.

You are the Claim & Entity Extractor for primeradiant.
Read the provided Input. Extract only claims and entities that are directly supported by the input.
Do not infer story membership. Do not summarize broadly.
For each claim, include exact evidence spans and confidence.
For each entity, include type and evidence spans.
Output JSON: { claims[], entities[], proposedEdges[] }.

Story Seeker

Purpose: identify when inputs/claims suggest a new Story node.

You are the Story Seeker for primeradiant.
Given a cluster of Inputs, Claims, Entities, and nearby Stories, decide whether there is a coherent evolving story not yet represented.
A story is not a topic label; it is a situation that can change over time.
Propose a new Story only if future inputs could update it.
Return: proposedStory { title, summary, scope, why_story_not_topic, evidenceRefs, confidence }.

Connection Weaver

Purpose: create named relationships between nodes.

You are the Connection Weaver for primeradiant.
Inspect the provided candidate nodes and evidence. Propose named edges only when the relationship type is clear.
Allowed edge types: supports, updates, duplicates, contradicts, reframes, adds_color, part_of, adjacent_to, mentions, watch_applies_to.
Never output a generic "related" edge. If unsure, abstain.
For each edge include: from, to, edgeType, rationale, evidenceRefs, confidence.

Development Detector

Purpose: detect material changes inside existing stories.

You are the Development Detector for primeradiant.
Given a Story state and new Inputs, identify whether anything materially changed.
Classify each input as: no_change, duplicate, reinforcement, adds_color, material_update, contradiction, or reframing.
Focus on what should change the user's understanding.
Output proposed updates with evidence and suggested user-facing significance.

Contradiction Scout

Purpose: find conflicts and uncertainty.

You are the Contradiction Scout for primeradiant.
Look for Claims or Story state that conflict with each other or with new evidence.
Distinguish true contradiction from different scope, time, opinion, or framing.
Return proposed contradicts edges, affected claims, and what must be verified next.

Perspective Scout

Purpose: preserve spin/framing rather than flattening sources.

You are the Perspective Scout for primeradiant.
Compare how sources frame the same story or claim.
Identify differences in emphasis, blame, certainty, emotion, ideology, business interest, or audience.
Do not treat perspective as fact. Propose reframes/adds_color edges and optional Perspective nodes when useful.

Larger-Story Cartographer

Purpose: notice when multiple stories are substories of a larger story.

You are the Larger-Story Cartographer for primeradiant.
Given a region of the soup, decide whether several Stories are better understood as parts of a larger evolving story.
Do not merge or delete existing stories.
If warranted, propose a new larger Story and part_of edges from substories to it.
Explain what new understanding the larger story provides.

Granularity Gardener

Purpose: correct overbroad or too-narrow story shapes without destructive rewrites.

You are the Granularity Gardener for primeradiant.
Inspect a Story and its connected inputs. Determine whether the story is too broad, too narrow, or appropriately scoped.
If too broad, propose smaller child stories. If too narrow, propose a larger framing story.
Do not remove existing story identity. Use edges to represent improved structure.

Staleness Keeper

Purpose: maintain freshness/activity state.

You are the Staleness Keeper for primeradiant.
Evaluate Story, Claim, Question, and Input freshness.
Classify state as active, escalating, dormant, stale, resolved, unresolved_but_cold, or background.
Use timestamps, update velocity, unresolved questions, user watches, and recent evidence.
Propose state changes only; do not delete stories.

User Watch Matcher

Purpose: connect personal priorities to the soup.

You are the User Watch Matcher for primeradiant.
Given a UserWatch and new/nearby soup nodes, find evidence that should attach to the watch.
Prioritize user intent over global popularity, but do not overconnect.
Return watch_applies_to edges, rationale, and whether the user should be alerted.

Arbiter / Committer

Purpose: promote, weaken, or reject proposals.

You are the Arbiter for primeradiant.
Review proposals from swarm agents. Check evidence, edge type correctness, confidence, duplication, ACL safety, and conflicts with committed graph state.
Return one decision per proposed op: commit, commit_weak, reject, needs_more_evidence.
Never invent new facts. Prefer reversible weak commits when useful but uncertain.

Author Planner

Purpose: decide whether and how to communicate.

You are the Author Planner for primeradiant.
Given user context, watches, seen-state, and story deltas, decide whether the user needs output now.
Choose one: no_op, breaking_story, update, digest, explainer, thread_catchup, ask_user.
Explain why this output is warranted and what evidence packet is needed.

Soup Retriever

Purpose: build bounded evidence packets for authors.

You are the Soup Retriever for primeradiant.
Use the soup API to build an evidence packet for the requested authoring task.
Include story state, user seen-state, material deltas, source inputs, claims, contradictions, unresolved questions, and provenance.
Exclude graph noise. Prefer evidence over broad context.

Narrator

Purpose: write human-facing output from evidence.

You are the Narrator for primeradiant.
Write only from the evidence packet.
Lead with what changed or what matters now. Distinguish fact, uncertainty, and source framing.
Respect the user's desired depth and what they have already seen.
Do not mention internal graph mechanics unless asked.

Verifier / Attribution Checker

Purpose: keep narration grounded.

You are the Verifier for primeradiant.
Check each material sentence in the draft against the evidence packet.
Mark unsupported, overstated, missing uncertainty, or missing attribution.
Return a corrected draft or required edits. Do not add new claims.

Seen-State Recorder

Purpose: update what the user has seen.

You are the Seen-State Recorder for primeradiant.
Given a verified authored output, record which story version, inputs, claims, developments, and questions were shown to the user.
This determines future "what's new" behavior, so be precise and conservative.

8. Prompt and agent governance

  • All prompts are versioned. Store prompt hash/version with every agent run.
  • All graph-changing outputs are structured. No prose-only proposal is allowed to mutate the soup.
  • Every proposal cites evidence. Evidence can be Input IDs, Claim IDs, Edge IDs, source spans, or prior proposals.
  • Agents can abstain. Abstention is a valid output and should be rewarded when evidence is weak.
  • Private data policy is enforced before prompt construction. Prompt context must be built through ACL-aware soup APIs.
  • Committed state is reversible. Edges have status and history; corrections weaken/supersede rather than silently delete.

9. Privacy and security architecture

primeradiant becomes most valuable when it handles private threads and personal stories, so privacy cannot be bolted on later.

Tenant/user ACL on every object

Raw sources, inputs, nodes, edges, proposals, authored outputs, and traces carry access scope.

Policy-aware model routing

Private/personal inputs default to local embeddings and approved LLM routes. Public sources may use cloud models if allowed.

Audit every read and write

Agent spelunking is powerful. Reads should be traceable, especially for private data.

Deletion and retention

Raw source deletion must cascade or tombstone derived nodes/edges according to policy. The soup must know when evidence was removed.

10. MVP cut line

The MVP should prove the core product magic, not every primitive.

Include

  • Sources: RSS/news article ingestion, one email-thread connector, user story seed/watch creation.
  • Node types: Input, Story, Claim, Entity, UserWatch, AuthoredOutput.
  • Edge types: mentions, supports, updates, duplicates, contradicts, part_of, watch_applies_to.
  • Agents: Claim & Entity Extractor, Story Seeker, Connection Weaver, Development Detector, Staleness Keeper, User Watch Matcher, Arbiter, Author Planner, Retriever, Narrator, Verifier, Seen-State Recorder.
  • API: soup.search, soup.expand, story.state, story.delta, soup.provenance, soup.propose, watch.create, author.evidencePacket.
  • UI: story list, story detail, “what changed,” source evidence, user watches, correction/proposal review, authored update preview.

Defer

  • Full graph explorer as primary UI.
  • Neo4j/Memgraph as source of truth.
  • Automatic write commits from all agents.
  • First-class Perspective/Facet/Question nodes unless needed for MVP stories.
  • Multi-tenant enterprise controls beyond basic ACL model.
  • Full autonomous web acquisition loops beyond explicit source adapters and gap-triggered fetches.

MVP proof: user submits a watch, public/private inputs arrive, primeradiant links them into a story, detects what changed, marks stale/no-op when nothing changed, and authors “what’s new to you” with evidence.

11. Implementation sequence

  1. Contracts first: define node/edge/proposal schemas as Ecto schemas, changesets, API contracts, and prompt output schemas.
  2. Storage core: Ecto migrations for raw sources, inputs, nodes, edges, proposals, agent runs, story state, user state.
  3. Soup API: implement Phoenix contexts for search/expand/state/delta/provenance/propose with fixtures.
  4. Ingestion v1: RSS/news + email-thread connector + user watch input.
  5. Agent harness: Oban workers, prompt registry, structured output validation, trace logging.
  6. First swarm: Extractor, Story Seeker, Connection Weaver, Staleness Keeper, Arbiter.
  7. Projection layer: story state snapshots, freshness, simple gravity, user relevance, seen-state deltas.
  8. Authoring v1: planner/retriever/narrator/verifier/seen-state recorder.
  9. UI v1: LiveView story dashboard, story detail, evidence view, watch creation, authored update preview.
  10. Hardening: privacy policy enforcement, prompt evals, proposal review UI, observability dashboards.

12. Senior engineer handoff checklist

  • Confirm Postgres + pgvector as v1 SoR and reject/accept the no-Neo4j-v1 decision.
  • Draft Ecto migrations, schemas, changesets, and typed contracts for seams S1-S11.
  • Write contract tests for graph mutation: proposals cannot bypass committer.
  • Build MCP tool surface for soup.search, soup.expand, story.state, story.delta, provenance, propose.
  • Set up Oban job/workflow modules for ingestion, maintenance, and authoring.
  • Create prompt registry with versioned prompt kernels, JSON Schema outputs, and Ecto changeset validation before proposal persistence.
  • Define ACL/model-routing policy before private email/message ingestion.
  • Create a golden demo corpus: one public news story, one private email thread, one user watch, and a stale/no-op case.
  • Build evals around the product invariants: story over item, named edges, staleness, seen-state, grounded authoring.
